# 1. Two Sum

<details>
<summary>📝 Problem Statement</summary>

Given an integer array `nums` and an integer `target`, return the **indices of the two numbers** whose sum is equal to `target`.

You may assume:

* Exactly **one valid solution** exists.
* The same element cannot be used twice.
* The answer can be returned in any order.

### Example 1

```text
Input: nums = [2,7,11,15], target = 9
Output: [0,1]

Explanation:
nums[0] + nums[1] = 2 + 7 = 9
```

### Example 2

```text
Input: nums = [3,2,4], target = 6
Output: [1,2]
```

### Example 3

```text
Input: nums = [3,3], target = 6
Output: [0,1]
```

### Constraints

* `2 <= nums.length <= 10⁴`
* `-10⁹ <= nums[i] <= 10⁹`
* `-10⁹ <= target <= 10⁹`
* Exactly one valid answer exists.

</details>

<details>
<summary>🐢 Brute Force — Try Every Pair</summary>

### Approach

The most straightforward idea is:

> For every element, try pairing it with every element after it.

For each pair `(i, j)`, check whether:

```text
nums[i] + nums[j] == target
```

If yes, return their indices.

We start `j` from `i + 1` so that:

* We don't use the same element twice.
* We don't check the same pair again.

### Code

```java
class Solution {

    public int[] twoSum(int[] nums, int target) {

        int n = nums.length;

        for (int i = 0; i < n; i++) {

            for (int j = i + 1; j < n; j++) {

                if (nums[i] + nums[j] == target) {
                    return new int[]{i, j};
                }
            }
        }

        return new int[]{-1, -1};
    }
}
```

### Complexity

* **Time:** `O(n²)`
* **Space:** `O(1)`

</details>

<details>
<summary>⚡ Better Approach — HashMap (Optimal if array is unsorted)</summary>

### Intuition

In the brute-force approach, for every `nums[i]`, we search through the remaining array to find the number we need.

Suppose the current number is:

```text
num = nums[i]
```

What number would complete the pair?

```text
needed = target - num
```

For example:

```text
nums[i] = 7
target = 9

needed = 9 - 7 = 2
```

So instead of searching through the remaining array every time, we can **remember the numbers we have already seen**.

We store:

```text
number → index
```

Then, when we see `num`, we simply ask:

> "Have I already seen `target - num`?"

If yes, we have found the answer.

### Why check the map before inserting the current number?

Suppose:

```text
nums = [3, 3]
target = 6
```

At the first `3`, the needed number is also `3`.

If we inserted the current element first, we could accidentally use the **same element twice**.

Instead:

1. Check whether the complement already exists.
2. If it doesn't, store the current number.

Thus, when we find a complement in the map, it always belongs to an **earlier index**.

### Algorithm

For every element:

1. Calculate the required complement:

   ```text
   target - nums[i]
   ```
2. Check whether the complement is already in the HashMap.
3. If yes, return its index and the current index.
4. Otherwise, store `nums[i] → i`.
5. Continue.

</details>

<details>
<summary>⚡ HashMap Code</summary>

### Code

```java
class Solution {

    public int[] twoSum(int[] nums, int target) {

        Map<Integer, Integer> map = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {

            int num = nums[i];
            int needed = target - num;

            // Complement was seen earlier
            if (map.containsKey(needed)) {
                return new int[]{map.get(needed), i};
            }

            // Store current number and its index
            map.put(num, i);
        }

        return new int[]{-1, -1};
    }
}
```

### Complexity

|              | Complexity     |
| ------------ | -------------- |
| ⏱️ **Time**  | `O(n)` average |
| 💾 **Space** | `O(n)`         |

HashMap lookup and insertion are **`O(1)` on average**.

> In pathological cases involving hash collisions, HashMap operations can be slower than `O(1)`. For Java's modern `HashMap`, heavily collided buckets can be treeified, giving `O(log n)` operations in those cases. For normal algorithmic analysis, we use **`O(n)` average time**.

</details>

<details>
<summary>🚀 Alternative — Two Pointers (When the Array Is Sorted)</summary>

### When is this useful?

If the array is **already sorted**, we can solve Two Sum using two pointers without a HashMap.

For example:

```text
[1, 2, 4, 7, 11, 15]
 ↑                 ↑
left              right
```

Calculate:

```text
sum = nums[left] + nums[right]
```

Now there are three possibilities.

### Case 1 — Sum is exactly the target

We found the pair.

```text
sum == target
```

Return it.

### Case 2 — Sum is too small

```text
sum < target
```

We need a **larger** sum.

Because the array is sorted, move `left` to the right:

```text
left++
```

This increases the value being added.

### Case 3 — Sum is too large

```text
sum > target
```

We need a **smaller** sum.

Move `right` to the left:

```text
right--
```

This decreases the value being added.

### Why does this work?

Because the array is sorted.

Moving:

```text
left → right
```

can only increase the left value.

Moving:

```text
right → left
```

can only decrease the right value.

Therefore, we can intelligently eliminate many pairs instead of checking all `O(n²)` pairs.

---

### If the array is already sorted

If we only need to know **whether a pair exists**, the two-pointer approach needs:

* `O(n)` time
* `O(1)` extra space

If we also need the **original indices**, we can still use two pointers, but we must preserve each element's original index.

</details>

<details>
<summary>💻 Two-Pointer Code — Returning Original Indices</summary>

If the input array is **not sorted**, we can store each element together with its original index, sort those pairs, and then apply two pointers.

```java
class Solution {

    public int[] twoSum(int[] nums, int target) {

        int n = nums.length;
        int[][] arr = new int[n][2];

        // Store {value, original index}
        for (int i = 0; i < n; i++) {
            arr[i][0] = nums[i];
            arr[i][1] = i;
        }

        // Sort by value
        Arrays.sort(arr, (a, b) -> Integer.compare(a[0], b[0]));

        int left = 0;
        int right = n - 1;

        while (left < right) {

            int sum = arr[left][0] + arr[right][0];

            if (sum == target) {
                return new int[]{arr[left][1], arr[right][1]};
            }

            if (sum < target) {
                left++;
            } else {
                right--;
            }
        }

        return new int[]{-1, -1};
    }
}
```

### Complexity

| Situation                                     |         Time |         Space |
| --------------------------------------------- | -----------: | ------------: |
| Array already sorted, only checking existence |       `O(n)` |        `O(1)` |
| Array already sorted + need original indices  |       `O(n)` | `O(1)` extra* |
| Unsorted array + sort first                   | `O(n log n)` |        `O(n)` |

*If the original indices are already available separately. The implementation above creates an `n × 2` array, so its extra space is `O(n)`.

</details>

<details>
<summary>🔍 Which Approach Should You Use?</summary>

The right approach depends on the **conditions of the problem**.

| Situation                            | Suitable Approach   |           Time |                           Extra Space |
| ------------------------------------ | ------------------- | -------------: | ------------------------------------: |
| Simple / no extra memory             | Brute Force         |        `O(n²)` |                                `O(1)` |
| Unsorted array + need indices        | **HashMap**         | `O(n)` average |                                `O(n)` |
| Already sorted + only need existence | **Two Pointers**    |         `O(n)` |                                `O(1)` |
| Already sorted + need indices        | Two Pointers        |         `O(n)` |  Depends on how indices are preserved |
| Unsorted + willing to sort           | Sort + Two Pointers |   `O(n log n)` | `O(n)` if original indices are stored |

### Important distinction

For the **standard LeetCode Two Sum problem**, the array is not guaranteed to be sorted and we need the **original indices**.

Therefore, the HashMap approach is the natural `O(n)` average-time solution.

The two-pointer approach becomes especially attractive when:

> **The array is already sorted.**

</details>

<details>
<summary>🧠 Pattern to Remember</summary>

For Two Sum, think:

### Unsorted array

```text
Current number
      ↓
What number do I need?
      ↓
target - current
      ↓
Have I seen it before?
      ↓
HashMap
```

### Sorted array

```text
left + right
    ↓
sum < target → left++
sum > target → right--
sum = target → found
```

The key observation for the HashMap approach is:

> **Instead of searching for the required number, remember what you have already seen so you can find it in constant average time.**

</details>
